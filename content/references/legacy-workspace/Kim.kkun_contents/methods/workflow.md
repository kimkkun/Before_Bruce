## 기획 세션 (수환이 아이디어·기사·헛소리를 던지면)
1. archive.md 최근 10건 + 해당 아이디어 검토
2. "하고 싶은 얘기 → 사장님이 듣고 싶은 질문"으로 뒤집기
3. `ideas/`에 소재 카드 작성 (`ideas/_template.md` 규격) — 필요 시 즉석 리서치로 근거 보강
4. **경험담은 기존 내용부터 확인**: 수환이 이미 말한 경험과 관련 자료를 먼저 확인한다. 기획·대본에 필요한 내용이 부족하거나 사례의 실재 여부가 불확실할 때만 빠진 부분을 질문한다. 충분히 확인된 경험은 다시 묻지 않고, 없는 일화·세부사항은 지어내지 않는다.
5. 카드 방향 컨펌 받고 종료 (컨펌 = 개입 ①)

## 대본 세션 (카드 확정 후)
수환에게는 제목 추천·도입 훅·전체 대본·캡션·썸네일 문구를 한 묶음으로 직접 제시한다. 파일에만 넣거나 대본만 전달한 상태를 촬영 준비 완료로 보고하지 않는다. 편집·Instagram 연결의 승인 범위와 실제 검증 상태는 [자동화 안내](automation.md#목표-흐름)를 따른다.

1. methods/reels-script.md 로드 → 출고 패키지 6종 생산 (POV 제목·훅 5·대본·캡션·썸네일 카피·블로그는 승인 후)
2. 내부 검수 통과 후에만 제출 (검수 룰은 reels-script.md)
   + **정량 검수 의무 (2026-08-20 채택, 2026-09-13 수환 “30초 이내로 맞추는게 맞다. 그렇게 통일해줘”로 측정 기준 확정)**: [작동 지침](../CLAUDE.md)의 핵심 주장·죄 전환·고백·서사 정체성과 실물 암시가 **영상 시작부터 30초 이내**에 드러나는지 확인한다. 대본 단계에서는 글자수와 발화 속도(5~6자/초)로 예상 시간 범위를 계산하고, 도입 상황극·무음·화면 전환 등 발화 외 시간도 포함해 해당 문구와 예상 등장 시각을 패키지에 기록한다. 도입 발화를 글자수에 포함했다면 그 시간을 중복 가산하지 않는다. 초안이 기준을 넘으면 제출 전에 재배치한다. 촬영·편집본이 생기면 실제 영상 시각으로 다시 확인하며, 예상 계산을 실측 검증으로 보고하지 않는다. (근거: 1티어 대본 3분 초과·고백 98초 지점을 측정으로 잡아냄)
3. 수환 승인 (개입 ②) → methods/longform.md 로드 → 블로그 초안
4. 산출물은 `drafts/`에 소재 슬러그로 저장 (대본·캡션·블로그 같은 접두)
5. **AI 초안·수환 수정본·실제 발화본 보존 (2026-09-10 수환 요청, 2026-09-13 “오케이 그렇게 해줘”로 세 버전 구분 재확인):** AI 초안과 수환 수정 원문은 같은 소재 접두의 별도 파일로 저장한다. 수환 원문은 오탈자까지 보존하고 검수·제안·촬영 발화로 덮어쓰지 않는다. “이대로 촬영” 등 명시적 확정은 수정본에 날짜·근거와 함께 표시하고, 초안과 NOW에서 그 촬영 정본을 연결한다. 같은 원문을 확정본 파일로 다시 복사하지 않는다. 촬영 발화가 달라지면 실제 발화본을 별도로 보존한다. 발화가 대본과 같다고 확인되면 기존 원문을 연결하고 확인 근거를 남긴다. 편집으로 발화가 달라지면 발행에 사용된 버전을 구분해 게시물 ID·URL·발행일 및 인사이트에 연결한다. 발행 사용본이 미확인이면 대본을 실제 발화본으로 단정하지 않는다.

## 대본부터 비컷·편집까지 — 2026-09-21 수환 확정

수환의 후속 요청으로 **대본 확정 → 기본 3~5장면 자율선정 → Higgsfield 이미지·영상 선제작 → 수환 검토 → 촬영본과 함께 편집**을 기본값으로 한다. 이전의 장면 제안마다 개수·상황을 먼저 승인받는 순서를 대체한다. 별도 비컷 지시를 기다리지 않으며, 수환이 지정한 컷·개수·제작 방식·보류 요청이 있으면 그 지시가 우선이다.

### 시작과 실행 범위

- 수환이 “이 대본으로 가자”, “대본 끝”, “이대로 촬영” 등으로 사용할 대본을 정하면 같은 작업에서 비컷 준비를 이어간다. 초안 제출·원문 보존·단순 파일 저장만으로 확정했다고 간주하지 않는다. 사용 대본이 불명확하면 비컷 기획까지만 진행하고 대본 버전만 확인한다.
- 자동 실행은 대화에서 에이전트가 도구를 이어 호출하는 방식이다. 폴더가 다른 에이전트를 자동 실행하거나 대화 종료 후 무인 감시가 돌아가는 구조가 아니다. 중단 시 기존 기록으로 재개한다.
- **자동 생성 예산: 영상 한 편당 총 최대 150크레딧.** 2026-09-21 수환이 비컷 3~5장면의 이미지·영상·교정 재시도 전체를 포함한 한도 질문에 “150크레딧 안쪽으로 해결해”라고 승인했다. 대본 확정 후 이 제작 범위는 컷별·이미지별 재승인 없이 진행한다. 150은 소진 목표가 아닌 상한이며, 더 적은 비용으로 통과하면 종료한다. 별도 충전·구독 구매·다른 서비스 결제는 포함하지 않는다. 편별로 다른 명시적 지시가 있으면 해당 범위를 따른다.
- 실행 전 해당 편의 기존 사용액·진행 중 작업의 예약 비용·새 작업 견적을 합산해 상한 안인지 확인한다. 버전 변경·세션 재개·피드백 수정으로 한도를 초기화하지 않는다. 차감 여부가 불명확하면 기존 작업 ID·실제 상태부터 확인하고 중복 제출하지 않는다. 예산 잔여와 누적액은 기존 편별 제작/편집 기록에, 작업별 비용은 생성정보에 남긴다.
- 최초 결과를 검수하고 핵심 결함이 있을 때만 원인을 바꿔 교정한다. 재시도도 편당 150크레딧 범위 안에서는 다시 묻지 않는다. 같은 실패를 조건 변경 없이 반복하지 않으며, 해결이 어렵거나 한도 안에 완료할 수 없으면 만든 결과·남은 문제·대안을 먼저 보여준다. 추가 지출은 [공통 승인 기준](../../WORKING-AGREEMENTS.md)에 따라 초과 이유와 필요한 추가 크레딧을 제시하고 승인받은 뒤 진행한다.

### 선제작 → 검토 → 촬영 → 편집

1. **대본과 기존 작업 확인:** 소재 ID, 사용할 대본 경로·버전/해시, 기존 장면표·컷 기록·서비스 작업 ID·로컬 결과·사용자 피드백을 확인한다. 이미 만든 컷은 재사용·수정 여부부터 판단하며, 대본 수정 시 영향을 받은 컷만 다시 검토한다. 같은 대본을 다시 열었다는 이유로 새 비용을 쓰지 않는다.
2. **3~5장면 선정:** 오프닝 시각적 훅·중간 환기·내용 이해에 필요한 상황을 고른다. 기존 대본 패키지에 장면표 하나를 두고 `S번호 / 대응 대사 / 보여줄 상황·목적 / 시작→변화→끝 / 예상 삽입 길이 / 제작 방식 / 컷 제작기록 링크`를 적는다. 서로 비슷한 컷으로 개수만 채우지 않는다. 별도 지시가 없으면 그 장면표대로 제작한다.
3. **Higgsfield 작업으로 연결:** 영상별 보관함이 없으면 이때 먼저 만들고, 실제 자료는 `99_작업보관/Higgsfield/제작방식/S번호_장면이름/` 한 곳에 둔다. [Higgsfield 입구](../../Higgsfield/README.md)에서 해당 편 보관함으로 연결한다. 사용자가 폴더를 옮기거나 자료를 다시 전달할 필요는 없다. 인물은 현재 확인된 김꾼 참고자료·Soul ID와 외형 조건을 따르며 안경 등 특징을 임의 추가하지 않는다.
4. **이미지 → 영상:** 해당 [제작 방식](../../Higgsfield/README.md)의 지침과 현재 모델 입력·비용을 확인하고 기준 이미지 제작 → AI 시각 검수 → 통과 이미지 영상화 → 다운로드·영상 검수까지 이어간다. 이미지 확인을 수환의 매번 중간 승인으로 만들지 않는다. 직접 촬영한 연기가 필요한 컷은 [추가 촬영 기준](../../Higgsfield/01_내%20연기%20변환/README.md#현재-제작-기준--2026-09-21-수환-확정)에 따라 대사·구도·동작을 미리 안내하고 그 컷만 원본 대기로 둔다. 상황/인물 생성으로 목적을 충족할 수 있으면 선제작하되 원본 연기 보존을 약속한 컷을 임의 대체하지 않는다.
5. **검토본 전달:** 각 컷에 실제 생성 조건·작업 ID·비용·검수 범위·사용 가능한 구간을 남긴다. 해상도·길이·재생/디코딩과 얼굴·손·사건·음향을 구분해 검사하고, 확인 못 한 부분을 표시한다. 컷 번호와 대본 연결을 보여주는 검토용 묶음을 해당 편 `99_작업보관/Higgsfield/검토본/`에 새 버전으로 저장하고 보관함/Higgsfield 입구에서 바로 찾게 한다. 생성 성공을 사용자 채택으로 간주하지 않는다. 수환은 결과 묶음에서 사용·수정·제외를 정한다.
6. **촬영 자료 접수:** 수환이 “촬영해서 편집하자”, “영상 작업 시작하자” 등으로 요청하면 해당 편 `01_자료넣는곳`을 없을 때만 만들고 Finder로 연다. 선제작 때 만든 폴더·비컷·참고자료는 그대로 재사용한다. 수환은 촬영본과 추가 참고자료만 넣으면 된다. 원본 투입 완료를 대화 또는 실제 파일로 확인하고 편집을 이어가며, 파일 투입 자체가 무인 실행을 뜻하지 않는다.
7. **기존 편집에 비컷 포함:** [기존 로컬 편집 범위](capcut-caption-style.md#다음-검증-순서--2026-09-11-수환-확정)에 따라 원본 배치·실제 발화 확인·타이트한 컷편집·자막·연출·음향·썸네일·내보내기를 수행한다. 수환이 채택한 비컷은 별도 삽입 지시 없이, **컷편집 후 실제 발화와 의미에 맞는 시각**에 넣는다. 토킹헤드와 수환 음성이 중심이며 생성 컷의 불필요한 음성이 겹치지 않게 한다. 수정/제외 컷은 넣지 않고 채택이 불명확한 컷만 확인한다. 사라진 대사에는 억지로 넣지 않는다. 최종 사용 버전·원출력 내 사용 구간·본편 삽입 시각·생략 이유를 편별 편집 기록에 남긴다.
8. **검수·복구:** 전체 출력의 자막·음향·비컷 전환·얼굴·참조파일을 확인하고 실제 검토 범위와 함께 전달한다. 대본 변경은 장면 설계, 이미지 결함은 이미지, 동작 결함은 영상, 타이밍 결함은 편집 단계로 돌아간다. 일부 컷 실패가 준비된 다른 컷을 막지 않으며, 미완료 컷은 수와 이유를 명시한다. 기존 원본·결과·수환 수정본은 덮어쓰지 않는다.

정본은 콘텐츠 한 편이다. 공통 제작법은 Higgsfield, 장면표는 대본 패키지, 컷별 채택·피드백은 제작기록, 실제 생성 조건은 버전 생성정보, 본편 타임라인은 CapCut 실제 프로젝트와 편별 편집 기록에 둔다. 이번 변경은 실행 절차의 연결이며, 전체 과정의 무인 자동화나 다음 편의 품질 재현을 검증한 것은 아니다.

## 영상 편집 세션

### 읽는 범위와 정보 정본

1. 프로젝트 공통 필독을 확인한 뒤, 대상 편 `drafts/YYYY-MM-DD_소재ID_video-comparison.md`의 **현재 상태** 절을 먼저 읽는다. 보관함 `03_수정기록/README.md`는 이 정본의 입구다. 새 편이면 같은 문서 하나에 현재 상태와 이력을 시작하며 별도 상태 요약을 만들지 않는다.
2. 공통 연출은 [편집 기준의 적용 안내](capcut-caption-style.md#적용할-기준과-과거-사례-구분), 실행 검증은 [단계별 실행 확인](automation.md#단계별-실행-확인--2026-09-19)만 읽는다. 각 문서 안의 옛 사례는 이번 판단에 필요할 때 해당 절만 찾아본다.
3. 실제 원본·활성 CapCut 프로젝트·출력 버전을 대조한다. 문서의 완료 표시나 가장 최근 파일 수정시각만으로 현재 상태를 단정하지 않는다. 기록과 실물이 다르면 확인된 사실·미확인 차이를 정본의 현재 상태에 반영한다. 확인 없이 과거 묶음으로 라이브 프로젝트를 덮어쓰지 않는다.
4. 현재 상태에는 `근거/확인일·진행 상태·비교 기준 버전·실제 파일/프로젝트·남은 피드백·다음 행동·검증 한계`만 유지한다. 완료된 수정은 미완료 목록에서 빼고 아래 이력에 남긴다. 이력의 날짜·버전·사용자 발언·이유·적용 범위·검증을 최신 상태와 섞지 않는다.
5. 폴더 README와 NOW는 이 정본에 연결만 한다. 공통 기준을 영상별로 복사하거나 날짜별 상태 사본을 쌓지 않는다. 지난 기록·작업보관·to delete를 기본 탐색 대상으로 읽지 않는다. 비교나 복원이 필요할 때만 근거 파일을 지정해 조회한다.
6. 사용자 확정·에이전트 관찰·미확인을 구분한다. 이번 편의 연출은 사용자 공통 적용 확정 없이 공통 취향으로 승격하지 않는다. 반복 오류는 실행 검사로 보완한다. 충돌은 현재 사용자 지시와 확인한 실물을 우선 대조하고, 해결되지 않은 해석은 미확인으로 남긴다.
7. 다음 영상 완료 시 같은 편집 기록에서 `작업 시간·불필요한 사본·동일 오류 재발·사용자 재수정`을 비교한다. 측정하지 않은 개선은 달성했다고 쓰지 않는다. 효과 없는 절차·중복 기준은 해당 정본에서 보완하고 새 관리 문서로 우회하지 않는다.

“영상 편집하자” 요청은 [자료 접수·결과 보관](../README.md#영상-파일-보관)과 [승인된 편집 범위](capcut-caption-style.md#다음-검증-순서--2026-09-11-수환-확정)를 따른다. 현재 편집 진행 승인이 없는 기록 정리 요청은 라이브 편집을 시작하는 승인으로 해석하지 않는다. 승인된 편집은 통상적인 단계별 재승인 없이 결과 검증까지 수행한다.

### 직접 수정 → 비교 → 다음 편 적용

사용자가 직접 수정 중이면 AI 기준본 ZIP을 고정하고 라이브 프로젝트는 건드리지 않는다. “수정 끝났어, 비교해봐” 요청 후 읽기 전용으로 현재 프로젝트를 확인한다. 재료 ID·JSON 키 순서만으로 차이를 판단하지 않고 시간·문구·스타일·음원·화면·스티커 배치를 의미별로 비교한다. 사용자 변경본은 그 시점의 한 버전으로 보존하고 차이·이유·이번 편/공통 여부를 기존 비교 기록에 연결한다. 이유를 모르는 연출은 관찰로 남긴다. 다음 편에서는 공통 확정 기준과 필요한 수정 사례만 적용하고 실제 출력을 대조한다. 다음 편 실증 전에는 재현 성공으로 보고하지 않는다.

### 기록 건강 검사와 사용자 알림

`python3 -B methods/editing_memory_check.py --episode YYYY-MM-DD_소재ID`를 편집/비교 시작 전, 피드백 기록 후, 결과 전달 전에 실행한다. 이번에 연결한 대상은 owner-emotions 편이며 과거 편을 재개할 때 그 편의 실제 비교 묶음·해시·피드백을 정본 안 `editing-state` 블록에 등록한다. 없는 기준본을 임의 선택하지 않는다.

- 검사 항목: 정본 절 중복·현재 링크 단절·비교 기준 해시 변경·반영 근거 없는 완료 표시·미확정 공통 승격·동일 속성의 확정값 충돌·완료 상태의 미반영 코멘트·결과 폴더 혼잡·선택 읽기 범위 크기.
- 숫자 경보는 현재 상태 3,500자, 기본 선택 읽기 14,000자, 과거 이력 30,000자 초과를 **검토용 초기 기준**으로 사용한다. 모델 한도나 품질 저하 확정 기준이 아니다. 임계값만 올려 경고를 숨기지 않고 중복·불필요한 과거 읽기부터 확인한다.
- 코멘트 목록 필드: `id/source/status(pending·applied·deferred)/scope(episode·common)/confirmed`; 반영 완료는 `evidence`에 정본 기준 상대경로, 공통 반영은 `rule_anchor`에 편집 기준의 실제 절 제목을 둔다. 같은 속성의 공통 확정은 `property/value`를 넣어 명시 충돌을 검사한다. 이전 결정을 대체할 때 이전 항목을 deferred로 바꾸고 대체 이유를 이력에 남긴다.
- 미반영 코멘트가 있는 사용자 수정 대기 상태는 정상이다. `review_state=ready`로 바꾸면서 pending이 남으면 오류다. 검사 성공은 범위 내 문제가 검출되지 않았다는 뜻이며 편집 완료나 취향 재현을 뜻하지 않는다.
- **경고 발생 시 사용자에게 먼저 짧게 알림:** `기록 점검: 무엇이 문제인지 / 어떤 오판 위험인지 / 제안하는 정리 / 영향받는 작업`. 기준 불명·충돌에 의존하는 편집은 해결 전 적용하지 않고, 독립적인 작업은 계속한다. 단순 링크·명확한 중복 정리는 승인된 범위에서 처리하되 원본·사용자 결정은 임의 변경하지 않는다.
- 의미상 상충·요약에서 빠진 코멘트·실제 총 프롬프트/토큰·모델 혼동은 이 도구만으로 감지할 수 없다. 에이전트가 원문과 현재 기준을 대조해 판단하고 불확실하면 알린다. 기록하지 않은 발언은 검출할 수 없으므로 피드백 접수 직후 목록과 사용자 원문을 대조한다.
- 이 검사는 **요청된 작업 중 실행**한다. 상시 감시·대화 밖 알림은 설치하지 않았다. 보고서 파일을 매번 추가하지 않고 경고·해결 근거만 기존 편집 기록에 남긴다. 자동으로 기준을 덮어쓰거나 파일을 삭제하지 않는다.

자동화 전환(2026-09-09): 반복 캡처 제출을 기본 전제로 삼지 않는다. [자동화 안내](automation.md)의 실제 연결 상태를 먼저 확인한다. API 수집이 검증되면 그 원본을 우선 반입하고, 발행 게시물과 대본 연결·원장 갱신까지 확인한다. 아래 수동 반입은 기존 자료와 API 미제공 항목의 보완 경로다. 예약 도구 실행 성공을 확인하기 전에는 리마인드를 걸었다고 말하지 않는다.

## 성과 리추얼 (2026-08-20 개정)
- **측정 시점 고정: 발행 후 7일 지표.** [7일차 관측 정의](automation.md#기록-위치와-성과-해석)에 따라 같은 게시물·관측 시점의 값끼리 계산한다. 다른 시점의 값은 경과일을 명기하고 7일차 순위에 섞지 않는다.
- API 수집 검증 후 자동 반입을 우선하고, 기존 수동 자료도 받는다 → **원본은 metrics/에 그대로 보존(raw — API 응답·스샷·숫자 원문, 고치지 않는다)** → 발행 게시물 연결 확인 후 archive.md에 기록 (summary, 규격은 archive.md 상단). 현재 수집기는 API 조회표 생성까지이며 원장 자동 갱신은 미구현이다.
- **성과 판정 정본 (2026-09-13 수환 “가장 효율적인 책정방법으로 통일시켜줘” 승인):** 핵심 지표는 아래 네 가지다. 원본 수치는 보존하고 비교용 비율을 함께 표시한다. 좋아요·저장은 참고용으로만 보며 추가 제출을 기본 요구하지 않는다.

| 핵심 지표 | 기록·계산 방법 |
|---|---|
| 조회수 | 해당 영상의 조회 횟수. 도달한 계정 수와 구분 |
| 평균 시청 시간 | 단위를 확인한 초 단위 값과 영상 길이를 함께 표시. 길이가 비슷한 영상끼리 비교하며 완주율로 부르지 않음 |
| 공유 | 원본 공유 건수 + 조회 대비 공유율 = 공유 ÷ 조회수 × 100(%) |
| 팔로우 전환 | 해당 영상에 귀속된 팔로우 수 + 만 조회당 팔로우 = 팔로우 ÷ 조회수 × 10,000 |

- **계산 조건:** 분자·분모는 같은 관측 시점·플랫폼의 값으로 맞춘다. shares·sends는 원본 지표명을 남기고 의미가 확인된 같은 지표끼리 비교한다. 계정 전체 팔로워 증감을 특정 영상의 팔로우 수로 대신하지 않는다. 조회수가 0이거나 필요한 값이 없으면 비율은 미산출로 두고, 누락을 0으로 채우거나 역산하지 않는다. 예전 도달 대비 공유율은 분모를 명시해 보존하고 조회 대비 공유율과 섞지 않는다.
- **판단·보고:** 최근 기록 중 경과일·목적·길이가 비슷한 영상과 비교해 「잘된 점 / 아쉬운 점 / 다음 편에서 바꿀 것 1개」를 짧게 보고한다. 비교 자료가 부족하면 판정을 보류한다. 목적별 지표를 임의의 종합점수로 합치거나 한 편의 결과를 원인으로 단정하지 않는다.
- 편별 추가 KPI가 있으면 같이 걷는다 (예: 모집 편 = 베타 지원 수, 참여형 = 댓글 수)
- 발행 후 7일 측정을 목표로 자동 수집 일정을 연결한다. 정기 실행·리마인드는 실제 등록과 실행 기록으로 확인하며, 대화 밖에서 이미 동작 중이라고 가정하지 않는다.

## 생산 규칙
- **램프업**: 1~2주차 주 2~3편 → 4주차에 성과·체력 보고 증편 판정. "주 5~6편"은 목표가 아니라 검증 대상 가설. 최소 유지 모드 = 주 1편 (0편 주간은 시스템 이상 신호 — 원인을 물어라).
- **자동화 범위**: 수환의 목표는 기록·편집·성과 수집·대본 개선 자동화다. 소재 방향·대본 승인 없이 확정 발행본으로 취급하지 않으며, 계정 게시·유료 생성·외부 전송은 승인 범위에서만 한다.
- **사례 실재 확인**: 대본 속 일화가 실제 경험인지 불확실하면 지어내지 말고 수환에게 확인 (일등고기 언급 절대 금지 — 폐업).
